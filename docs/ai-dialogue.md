## 2. 关键设计决策

**AI 提出并落地**：
- 「不丢失」边界：数据库是唯一真相源，先落库（WAITING）再入队；用编程式事务确保入队失败时不回滚已落库任务，由恢复扫描兜底。
- 幂等：`business_key` 唯一索引 + 乐观锁 CAS 领取。
- 重试治理：失败任务落库为 `RETRY_WAITING` + 退避时间，由调度器延迟重新入队，避免失败瞬间挤占队列。

## 3. 问题排查记录

**问题 1**：H2 2.2.224 报错 `AUTO_SERVER=TRUE && DB_CLOSE_ON_EXIT=FALSE` 不支持。
**解决**：去掉 `AUTO_SERVER`（单进程文件模式不需要），保留 `DB_CLOSE_ON_EXIT=FALSE;WRITE_DELAY=0` 保证提交即落盘。

**问题 2**：重试任务卡在 `RETRY_WAITING`，调度器报错 `Function "UNIX_TIMESTAMP" not found`（MySQL 专有函数）。
**解决**：MyBatis XML 中三处 `UNIX_TIMESTAMP() * 1000` 改为 Java 传入 `#{now}` 时间戳参数，同步调整 Mapper 方法签名与调用方。修复后验证任务历经 3 次退避重试正确进入死信。

**问题 3**：并发测试失败（纯生产者无消费者，队列填满后 offer 超时）。
**解决**：测试改为 3 生产者 + 2 消费者并发，验证不丢任务且无重复消费；同时修正在测试配置中补上 MyBatis mapper-locations。

## 5. 自测三专项（对应用户要求 2）

用户要求验证三点：状态流转与数据一致、异常不丢失可恢复、队列边界数据正常。

**AI 执行与结论**：

- **状态流转 / 数据一致性**：提交 flow-success、flow-retry、flow-fatal 三类任务。停应用后用 H2 Shell 直查库核对：SUCCESS 任务数 = 结果表行数 = 1，非终态残留 0；flow-retry 历经 3 次退避进死信（retry_count=3、version=11），flow-fatal 直接死信，时间戳 created ≤ started ≤ finished 全部成立。
- **异常不丢失 / 重启恢复**：提交 15 个慢任务制造积压（11 WAITING + 4 RUNNING），用 `SIGKILL` 强杀（绕过优雅停机）。查库确认 15 条全部落盘；重启后 4 个僵死 RUNNING 被重置重入队，最终 14 SUCCESS + 1 DEAD_LETTER（随机失败），15 记录 / 15 唯一键 / 14 结果行，无丢失无重复。
- **队列边界**：批量 30 任务背压正常（队列有界）；10 个并发请求提交同一 key，库中仅 1 条、返回同一 taskId（幂等生效）；单线程 + 阻塞任务验证出队顺序 high(9)→mid(5)→low(1)。
- **发现的非数据瑕疵**：并发幂等命中且队列恰满时，重复提交返回 `QUEUE_FULL` 而非同一 taskId（无重复、无丢失，仅返回语义可优化），已如实报告用户。
